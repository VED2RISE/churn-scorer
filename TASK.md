# Python-секция: практическое задание (45–60 минут)

Проект **churn-scorer** — небольшой пайплайн команды роста: по журналу событий продукта
считаем признаки пользователей и обучаем модель риска ухода. Описание проекта, данных и
команд — в `README.md` внутри архива.

Можно и нужно использовать привычные AI-инструменты (Claude, Codex, Cursor и т.п.).
Проговаривай вслух, что делаешь и почему: нам важен не только результат, но и то, как ты
работаешь с AI — что ему даёшь, как проверяешь ответы, как принимаешь решения.

## Подготовка (2–3 минуты)

1. Склонируй репозиторий (ссылку пришлёт интервьюер) или распакуй `churn-scorer.zip` —
   рядом с папкой `candidate-python-environment`:

   ```bash
   git clone <ссылка> churn-scorer
   ```

2. Активируй подготовленное окружение и убедись, что всё работает:

macOS / Linux:

```bash
cd churn-scorer
source ../candidate-python-environment/.venv/bin/activate
python -m pytest -q
```

Windows PowerShell:

```powershell
cd churn-scorer
& "..\candidate-python-environment\.venv\Scripts\Activate.ps1"
python -m pytest -q
```

Ничего доустанавливать не нужно: все зависимости уже в `.venv`.

## Обязательно по ходу работы

- Перед изменениями и после каждого изменения прогоняй тесты и проверку типов:

  ```bash
  python -m pytest -q
  python -m mypy churn
  ```

  В конце оба должны быть зелёными. На новое поведение добавляй тесты.
- Новые пакеты не ставим: решение должно работать в подготовленном `.venv` как есть.
- Проговаривай, что делаешь: какой запрос даёшь AI, что из его ответа проверяешь и как.

## Часть 1. Найти и исправить проблему (~20 минут)

Сообщение от продакт-менеджера:

> Модель на валидации показывала AUC почти 1.0, мы радостно запустили пилот на новой когорте.
> По итогам пилота команда удержания говорит, что список «рискованных» почти случайный:
> на holdout AUC ≈ 0.72. Почему такая разница? Это ошибка в данных, в коде или нам просто
> не повезло с когортой?

Воспроизведение:

```bash
python -m churn train
python -m churn evaluate
```

Ожидаем:

- объяснение причины (что именно и почему даёт такой эффект);
- исправление в коде;
- доказательство, что проблема решена (метрики до/после и/или тест, который ловит регрессию).

## Часть 2. Небольшое улучшение (~20 минут)

Предложи и реализуй **одно** небольшое продуктово-техническое улучшение проекта. Сначала
коротко обоснуй выбор (кому и зачем это нужно, что откладываешь), потом делай.

Примеры, можно своё:

- в `score` добавить «причины риска» для каждого пользователя (какие признаки больше всего
  повлияли) — чтобы команда удержания понимала, почему человек в списке;
- валидация входных данных перед обучением: fail-fast на дубликаты событий, неизвестные
  типы, события «из будущего» относительно cutoff, пользователей без меток;
- сохранять вместе с моделью метаданные (дата обучения, cutoff, метрики, список признаков)
  и проверять их при `evaluate`/`score`;
- сделать окно признаков настраиваемым (7/14/30 дней) и сравнить качество;
- любое другое, которое ты считаешь более полезным — объясни, почему.

## Часть 3. Объяснение (~10 минут)

Коротко расскажи:

- как устроено решение end-to-end (данные → признаки → модель → скоры);
- в чём была ошибка и почему метрика врала; как не допустить такой класс ошибок в будущем;
- как ты работал с AI: что просил, что проверял руками, где он ошибся или увёл не туда,
  какие решения принял сам.
